## 0. 検証したい命題

> **同じ指の `NailSocket` に別の日の爪を差し替えても、「同じ自分の手」に見えるか。**

Personal Hand Base + Replaceable Nail Set 構想の成否を決める唯一の未検証リスク。

Web 側では既に確認済み: **同一 socket に別の NailSet を載せても配置行列は完全に一致する**
（`tests/nail3dGeometry.test.ts`「two NailSets on the same socket produce identical placement」）。
したがって「手が揺れる」原因は **socket 推定側にしか存在しない**。

## 1. どの環境・リポジトリで実装すべきか

### 1.1 現状の制約

| | |
|---|---|
| iOS 実装 | **このリポジトリに存在しない**（`ios/`, `AVCapture`, `VNDetectHumanHandPose`, `NailGeometry` すべて grep 0 件） |
| 所在 | アカウントのリポジトリ一覧にも nail-report 対応の iOS リポジトリが見当たらず、オーナーのローカル環境にのみ存在すると見られる |
| 影響 | AI パイプライン（Jules / Codex / Claude）から読めず、CI も回らず、レビューもできない |
| 既にあるもの | **macOS ホストで動く検出ベンチ（#360 で sim → ホスト実行に移行済み）** |

### 1.2 ここで効く重要な事実

**socket 安定性の測定に写真は要らない。**

socket 推定の入力は「21 landmarks ＋ 爪領域の四隅」であり、どちらも**数値**。
テクスチャ生成には画像が要るが、それは本 PoC の測定対象ではない。

| 帰結 | |
|---|---|
| プライバシー | 実写をリポジトリに入れずに済む（`IOS_CAPTURE_REQUIREMENTS.md` の方針とも整合） |
| 実行環境 | 数値 JSON なら **このリポジトリの CI で回せる** |
| 反復速度 | TypeScript + node test runner で、WebGL も実機も不要 |

### 1.3 推奨: 3 層に分ける

```
[1] landmark / 爪領域の抽出        … macOS BenchTool（既存・#360）を拡張して JSON ダンプ
         ↓ 数値 JSON（写真は含めない）
[2] socket 推定と安定性評価        … このリポジトリ（TypeScript / node / CI）  ← PoC の本体
         ↓ 有望なら
[3] Swift へ移植して実機確認        … iOS（本番の責務分離どおり）
```

#### なぜ [1] を既存 BenchTool にするか

MediaPipe と Vision ではランドマークのノイズ特性が違うため、**MediaPipe で測った安定性は Vision に転移しない**。
既存 BenchTool は本番と同じ Vision を使い、かつ #360 で macOS ホスト実行になっているので、
**JSON ダンプを足すだけ**で本番相当のノイズを持つ実験データが得られる。iOS 側の追加実装はこれだけで済む。

#### なぜ [2] をこのリポジトリにするか

| 理由 | |
|---|---|
| 反復 | socket 推定式の調整は何十回も回す。実機ビルドを挟まない方が速い |
| 検証 | 既存の `tests/` 基盤（node test runner・CI）にそのまま乗る |
| 可視化 | 生成した CND を `/nail3d-preview` に読ませれば**契約適合が目視で分かる**（不適合なら L0 に落ちる） |
| レビュー | 実験条件・指標・しきい値が git に残り、パイプラインから見える |

#### 責務分離（案 A-1）との関係

**矛盾しない。** A-1 は**出荷する製品**の責務分離であり、本 PoC は研究。
PoC の成果物は「数値と判断」であってコードではない。有望と判明したら [3] で Swift に移植し、
そこからは A-1 どおり iOS が Detection / Reconstruction を持つ。

### 1.4 別件として推奨: iOS アプリの private リポジトリ化

**#405 のブロッカーではないが、やらない限り片側が永久に見えない。**

| | |
|---|---|
| 得られるもの | バージョン管理・レビュー・macOS runner での CI・#391 のベンチ資産とマニフェストの追跡 |
| 必須条件 | **private であること。** `ios/BenchmarkAssets/angles/real/` はオーナー本人の爪の実写であり、public は不可 |
| 実写の扱い | 画像は git に入れず、`.gitignore` ＋ ローカル保持（または LFS）。**git に入れるのは landmark / quad の JSON だけ** |

## 2. 最小の撮影入力

### 2.1 何が分散を生むかで決める

| 撮り方 | 測れるもの |
|---|---|
| 手を動かさず連写 | センサ・検出器のノイズだけ（**不十分**） |
| **手を一度フレームから外し、置き直して撮る** | 再提示によるばらつき ＝ **実際の記録間で起きること** |

したがって **「セッション」= 手を一度どけて置き直す**と定義する。これが最小単位。

### 2.2 最小セット

| | 量 | 理由 |
|---|---:|---|
| 指 | **1 本**（人差し指 or 中指） | 最も平坦で検出しやすい。5 本への展開は #394 |
| セッション | **5** | セッション間分散の推定に最低限必要 |
| セッション内フレーム | **3** | セッション内 / 間の分散分解に必要 |
| 角度 | **手の甲（上から）のみ** | 多角度は #390 の仕事。socket 安定性は単一角度で測れる |
| **ネイル変更後セッション** | **1**（計 3 フレーム） | **製品主張そのものの検証**（爪が変われば socket も動くのか） |

**合計 18 枚。** 同一照明・同一背景でまず 1 バッチ。

### 2.3 追加バッチ（頑健性・任意）

照明 / 背景 / 手の向きを変えて 3 セッション追加（9 枚）。1 バッチ目が合格した場合のみ。

### 2.4 ⚠ 絶対スケールは単写真では決まらない（未解決の契約論点）

`NailSocket.bedWidth` / `bedLength` は**メートル**で定義されているが、**単眼 1 枚の写真から絶対長は出ない。**

本 PoC での扱い:

> **安定性は「正規化単位」で測る。** 同じ指の近位指骨長などの骨格基準長で割り、スケールフリーにして比較する。
> 絶対スケールは本 PoC の対象外。

絶対スケールの選択肢（別途判断が必要）:

| 案 | 評価 |
|---|---|
| ARKit / LiDAR の深度 | 正確だが Pro 系端末に限定。iOS 実装が増える |
| 基準物を一緒に写す（コイン・定規・印刷マーカー） | 確実だが撮影体験が重くなる（Product Principle と衝突） |
| 初回キャリブレーションで一度だけ実寸入力 | 一度きりなので記録フローは重くならない |

**契約は metres を要求しているため、いずれ決めねばならない。** 本計画では論点として明記するに留める。

## 3. socket 安定性の測定方法

### 3.1 前提: どの座標系で比べるか（最重要）

カメラ座標系の socket をセッション間で比べても**無意味**（手が動いているだけ）。
**手自身の正準フレーム（canonical hand frame）に載せて初めて比較できる。**

```
各キャプチャについて:
  1. landmarks から正準フレームを作る
       原点   = 対象指の MCP
       軸     = MCP→PIP（指軸）と手のひら平面から正規直交化
       スケール = 近位指骨長で正規化
  2. socket をこのフレームで表現する
  3. セッション間で比較する
```

> **正準化が不安定なら、その下流はすべて不安定。**
> したがって**正準フレーム自体の安定性も別指標として測る**（下記 M0）。

### 3.2 指標

すべて正準フレーム上・骨格長で正規化。

| | 指標 | 定義 |
|---|---|---|
| **M0** | 正準フレーム安定性 | フレーム回転のセッション間測地角 RMS（度）。これが大きければ以下は読めない |
| **M1** | 位置ばらつき | `‖origin_i − median(origin)‖` の RMS と p95。**bedLength に対する %** |
| **M2** | 法線ばらつき | `normal_i` と平均法線の角度 RMS / p95（度） |
| **M3** | 指軸ばらつき | `tangent_i` について同上（度） |
| **M4** | 寸法ばらつき | `bedWidth` / `bedLength` の変動係数 CV（%） |
| **M5** | **分散分解** | セッション**内**分散 vs セッション**間**分散 |
| **M6** | **差し替え不変性** | ネイル変更前後の socket 変位（M1・M2 と同じ単位） |
| **M7** | **知覚判定** | 同一 NailSet を各セッションの socket で描画し、並べて見る |

#### M5 の読み方（原因の切り分け）

| 結果 | 意味 | 打ち手 |
|---|---|---|
| 内 ≈ 間（ともに小） | 安定 | そのまま採用 |
| 内 小 / 間 大 | **検出器ではなく正準化・推定式が原因** | F2 骨格拘束 / F1 固定（§5） |
| 内 大 | 検出器ノイズが支配的 | F4 多フレーム統合、撮影ガイド改善 |

**これを測らずに「ダメだった」と結論してはいけない。** 原因で打ち手が変わる。

#### M6 が本命

爪が変わったときに socket が動くなら、Hand Base + Nail Set の前提そのものが崩れる。
M1 と同じ許容内に収まることが必須。

#### M7 の手順（数値より先に効く）

1. `nailset-valid-full.json` をベースに、socket だけ各セッションのものに差し替えた CND を作る
2. `VITE_ENABLE_NAIL3D=true` で `/nail3d-preview` に読ませる
3. 2 枚並べ、**どちらがどのセッションか分からないか**を見る

### 3.3 しきい値は先に決めない（知覚から逆算する）

> **数値を先に決めて当てはめるのではなく、M7 で「違いが見え始める点」を見つけ、そこに数値ゲートを置く。**

手順:

1. socket を**人工的に** 2% / 5% / 10% / 20%（bedLength 比）ずらした描画を用意する
2. オーナーに並べて見てもらい、**どこから「爪が動いた」と感じるか**を記録する
3. その値を M1 のしきい値にする。M2 も同様に角度で行う

初期仮説（この較正で上書きする）: 位置 5% / 角度 5°。
これは当て推量ではなく**出発点**であり、較正結果が正とする。

## 4. 成功 / 失敗の判定基準

M7 の較正（§3.3）で確定した値を `T_pos` / `T_ang` とする。初期仮説は 5% / 5°。

| 判定 | 条件 | 次の行動 |
|---|---|---|
| **合格** | M1 ≤ `T_pos` かつ M2・M3 ≤ `T_ang` かつ M4 ≤ 5% かつ **M6 ≤ `T_pos`** かつ M7 で見分けがつかない | Swift へ移植（§1.3 の [3]）。#394 で 5 本へ展開 |
| **条件付き合格** | M1 ≤ 2×`T_pos` / M2 ≤ 2×`T_ang` の範囲。M7 で「言われれば分かる」程度 | **F1 ＋ F2 を適用**して再測定（§5）。改善すれば合格扱い |
| **不合格** | 上記を超える、または **M6 が M1 より明確に悪い**（爪を変えると socket が動く） | §5 の F1 / F3 を前提にした設計へ切り替え。自動推定を毎回行う案は捨てる |
| **測定不能** | M0 が大きく正準フレーム自体が不安定 | socket 以前の問題。landmark 品質（#400 / #361 / #363 / #365）に戻る |

### 4.1 判定の重みづけ

| | |
|---|---|
| **一次指標** | **M7（知覚）と M6（差し替え不変性）** |
| 二次指標 | M1〜M4（M7 の代理指標。CI で回せるのが利点） |
| 診断用 | M0・M5（原因の切り分けに使う。合否そのものには使わない） |

**「±0.25 以内」のような #391 / #394 の数値基準は socket 安定性には使えない** — あれは爪形状パラメータの推定精度の話。

### 4.2 PoC の成果物

- 実験データ（landmark / quad の JSON、写真は含めない）
- 指標の算出コードとテスト（このリポジトリ・CI でガード）
- M0〜M7 の実測値と、較正で決めた `T_pos` / `T_ang`
- 判定と、不合格なら §5 のどれを採るかの推奨
- `/nail3d-preview` で見た所見（スクリーンショット）

## 5. 失敗した場合の代替案

安い順・適用しやすい順。**F4 と F1 は合格した場合でも採る価値がある。**

### F4. 多フレーム統合（常に採用してよい）

セッション内の複数フレームから、位置は中央値、回転はクォータニオン平均、
外れ値は棄却し、**landmark 信頼度とブレ指標（#390 が既に算出）で重み付け**する。

| | |
|---|---|
| コスト | 低 |
| 効くケース | M5 でセッション内分散が大きいとき |
| 備考 | 単一フレームから socket を決める設計自体を避けるべき |

### F2. 骨格拘束（最有力の改善策）

socket を自由に 11 自由度（origin 3 ＋ normal 3 ＋ tangent 3 ＋ 寸法 2）で推定せず、
**指の骨フレームに拘束**する。

```
origin  = 末節骨上の固定比率の点
normal  = 末節骨の背側方向
tangent = 骨軸
自由なのは「比率」と「幅倍率」の数スカラーだけ → 平均で潰せる
```

| | |
|---|---|
| コスト | 中 |
| 効くケース | M5 でセッション間分散が支配的なとき |
| **懸念** | DIP / TIP ランドマークの品質に依存する。**このリポジトリの履歴が示す弱点そのもの**（#361「指を丸めた/クローズアップ構図で tip-DIP 直線補間モデルが破綻する」、#363 交差ポーズでの混線、#365 幾何整合性チェック） |
| 対策 | #365 の幾何整合性チェックを socket 推定の前段に入れ、破綻フレームを捨てる |

### F1. 初回キャリブレーション固定（**設計としては本来こちら**）

socket を記録ごとに推定し直さず、**キャリブレーションで一度決めて HandProfile に固定**する。
以後のスキャンは `NailGeometry` / `NailTexture` だけを生成する。

| | |
|---|---|
| コスト | 中（キャリブレーション導線の UX が要る） |
| 効果 | **分散は構造的にゼロになる** |
| 整合性 | **A-1 の設計と元から一致している。** HandProfile は「handedness ごとに 1 つ、再利用する」と定義済みで、毎回推定し直す前提ではなかった |
| 注意 | 悪いキャリブレーションが焼き付く → N 回の中央値＋品質ゲート（ばらつきが大きければ撮り直しを促す）で担保する |
| 再キャリブレーション | 体型変化・怪我・長期経過で必要。導線を用意する |

> **つまり PoC が問うているのは「毎回推定できるか」ではなく「キャリブレーションを数枚から確実に作れるか」。**
> 不合格でも F1 があれば構想は死なない。

### F3. 手動補正（確実だが摩擦がある）

自動推定の上から、オーナーが socket の位置・角度・大きさを一度だけ微調整する UI。

| | |
|---|---|
| コスト | 中〜高（UI。G2 design-review） |
| 効果 | **確実** |
| 前例 | iOS 側に**既に「調整」シートがある**（#393 指ごとの形状調整、#395 / #398 指セレクタ）。socket への拡張は一貫している |
| Product Principle との関係 | **抵触しない。** 禁じているのは「記録フローを重くすること」。これは記録ごとではなく**手ごとに一度**のキャリブレーション導線であり、保存パスの外にある |

### F5. 5 本同時拘束

5 本の socket を独立に推定せず、**手全体として同時フィット**する
（socket は手を横切る滑らかな弧の上に乗る、サイズは親指→小指でおおむね単調）。
外れた指を他の指から補正できる。#394（5 本分離）の上に乗る。

### F7. 深度センサ（ARKit / LiDAR）

単眼幾何が限界なら深度を使う。**絶対スケール問題（§2.4）も同時に解決する。**
ただし対応端末が限られ、iOS 実装が増えるため**先に試す手ではない**。

### F6. 2.5D への製品的退避（最終手段・ただし敗北ではない）

socket をどうしても安定させられない場合、**爪を手に配置することを諦め、L1（2.5D）で出す**。

| | |
|---|---|
| 実装状況 | **契約・レンダラーともに対応済み**（L1 は HandProfile 不要、`buildFlatLayout` 実装済み・テスト済み） |
| 失われるもの | 手に 10 本が載った絵（#392）、解剖学的な配置 |
| **残るもの** | **実物のネイルを 3D で残す・回す・振り返る・360°で見せる** |

> Nailous の本質「残す・振り返る・見せる」は **L1 だけでも成立する。**
> F6 は構想全体の失敗ではなく、到達レベルの引き下げである。

### 適用順

```
F4（常時） → F2（M5 がセッション間優位なら） → F1（設計として推奨）
   → F3（確実性が要るなら） → F5（5 本展開時） → F7（スケール問題と併せて）
   → F6（製品的退避）
```

### canonical hand frame の定義（確定）

```
原点    = 対象指の MCP
+y     = 指軸（MCP → PIP）
+z     = 手のひら法線（手首・人差し指 MCP・小指 MCP から）を +y に対して再直交化
スケール = 近位指骨長（MCP–PIP）
```

手のひら法線に**指自身のランドマークを使わない**のが要点。指先 1 点のノイズでフレーム全体が回らない。

### 検証できた性質

| | 検証内容 | 結果 |
|---|---|---|
| **不変性** | 平行移動・回転・一様スケール（および 3 つの合成）に対し socket が不変 | 1e-9 以内で一致 |
| **正規化単位** | 手を 0.05 倍 / 20 倍しても `bedWidth` / `bedLength` が変わらない | **メートルでないことの挙動的証明** |
| **人工摂動** | 2 / 5 / 10 / 20 % の原点シフトを注入 → 実測が注入値と一致 | 誤差 2% 以内 |
| | 2 / 5 / 10 / 20 度の傾きを注入 → 実測が注入値と一致 | 誤差 0.05 度以内 |
| | シフトは向きと寸法を動かさず、傾きは原点を動かさない | 相互汚染なし |
| **ノイズ分離** | 爪四隅のみにノイズ → **M0 は厳密に 0**、M1 / M2 のみ上昇 | 原因の切り分けが効く |
| | ランドマークにノイズ → M0 が上昇し、σ に応じて単調増加 | |
| **M5** | セッション内ジッタのみ → ratio < 1（内優位） | |
| | セッションごとのバイアス → ratio > 3（間優位） | |

### Stage 1 で判明したこと

#### 1. socket は「爪床」から読まねばならない（契約の読み方の明確化）

`NailSocket.bedLength` は契約で「爪床の実寸長。爪そのものの長さは含まない」と定義されている。
**検出が爪全体の輪郭を返す場合、爪床と自由端を分離しないと M6 が破綻する。**

合成で意図的に再現したところ、自由端込みの輪郭では爪が伸びるだけで `bedLength` が 50% 以上変わり、
自由端の反りでフィット平面が 5 度以上傾いた。**実写段階に入る前に、検出側が爪床を返せるかを確認する必要がある。**

#### 2. テストが生成器のバグを検出した（評価器が働いている証拠）

初版の合成ハンドは**手首だけ姿勢変換を適用し忘れていた**。手首は手のひら法線の計算に使われるため、
平行移動で socket がずれる一方、回転では（原点周りの回転で手首が動かないため）素通りした。
**平行移動不変性のテストだけがこれを捕らえた。** 片方だけでは不十分だった。

#### 3. 角度の「ゼロ」は 1e-4 度で測る

`acos` は 1 付近で精度が落ちるため、倍精度で同一な方向どうしでも 1e-6 度程度の差が出る。
角度のしきい値をこれより細かく設定してはいけない。テストでは `ANGLE_EPS_DEG = 1e-4` を使う。

### 絶対スケールの分離（厳守事項）

| | |
|---|---|
| 型 | `NormalizedNailSocket` は契約の `NailSocket` とは**別の型**で、`units: 'normalized'` / `scaleReference: 'proximalPhalanx'` を持つ |
| 変換 | **メートルへ変換する関数は意図的に存在しない** |
| 流出 | `NormalizedNailSocket` は `src/` の契約型・レンダラー側から一切参照されていない |
| 検証 | スケール不変性テストが「メートルでないこと」を挙動として示す |

**正規化値を CND の meter 値として保存する経路は存在しない。**

### Stage 1 の限界（実写前に認識しておくこと）

| | |
|---|---|
| 爪四隅が 3D | 合成では 3D の四隅を与えている。実際は 2D マスク由来であり、**2D→3D の持ち上げが別の誤差源**になる |
| 推定器はベースライン | 骨格拘束（F2）・多フレーム統合（F4）は未実装。Stage 1 は「自由推定」の素の性能を測る土台 |

## 6-B. 知覚較正 UI と測定手順 — 2026-10-06

```bash
VITE_ENABLE_NAIL3D=true npm run dev   # → /nail3d-calibration
```

### 何を見せているか

**同じ NailSet を同じ手に載せ、片方だけ socket をずらした 2 面を並べる。**
製品で起きる失敗（セッション間で socket がぶれ、別日のネイルを差し替えたときに手が動いて見える）を、
そのまま静止画の比較に落としたもの。

### 操作できる摂動（1 軸ずつ独立）

| 次元 | 内容 | 範囲 | 指標 | しきい値 |
|---|---|---|---|---|
| 位置ずれ | origin を爪床長の比で平行移動。方向は **横 / 指の長手 / 法線** | 0〜30% | M1 | `T_pos` |
| 法線の傾き | 指軸まわりに法線を回す（tangent は不変） | 0〜20° | M2 | `T_normal` |
| 指軸の回転 | 法線まわりに指軸を回す（normal は不変） | 0〜20° | M3 | `T_tangent` |
| 寸法スケール | `bedWidth` / `bedLength` を倍率で変更。**縦横とも / 幅のみ / 長さのみ** | 0〜40% | M4 | `T_size` |

スライダーは連続（位置・寸法 0.2% 刻み、角度 0.1° 刻み）。

### 測定手順（上昇法 / ascending limits）

1. 試行開始時スライダーは 0。**どちらをずらすかは毎回ランダム**
2. 「同じ手に見えなくなった」と感じるまで上げる
3. **「ここで違和感が出た」** で記録 → ずらしていた側が開示される
4. 分からなければ **「上限まで分からない」**（打ち切り）
5. 「次の試行」で繰り返す。各次元で複数回
6. **中央値が候補しきい値**として表示される。JSON をコピーして保存

### バイアス対策

| | |
|---|---|
| 左右のランダム化 | 「いつも A が変」という位置の思い込みを防ぐ |
| **キャッチ試行（20%）** | 無摂動の試行を混ぜる。ここで押したら誤検出として数え、表に出す。押す癖がしきい値を下げるのを可視化する |
| 共有カメラ | 2 面は基準側から計算した 1 つのフレーミングを共有（下記） |
| 摂動ゼロでの同一性 | 摂動ほぼ 0 で 2 面の描画差はアンチエイリアス相当（画素差 0.08%）。左右に系統差なし |

### ⚠ カメラを共有しないと測定にならない

各ビューが自分のジオメトリから自動フレーミングすると、**寸法の違いはスケール正規化で消え、位置ずれも中心合わせで薄まる**。
測ろうとしているものがちょうど見えなくなる。

対策として `cameraFraming()` を `nail3dGeometry` に切り出し、`framingFor()` が**基準側から 1 つだけ**計算して両ビューに渡す。
`Nail3DView` は `framing` prop があるとき自動フレーミングを行わない。

### 記録値の読み方（混同するとしきい値が 2 倍ずれる）

| | 意味 |
|---|---|
| **2 枚間の差（pairwise）** | 注入量そのもの。**`T_*` はこちらで記録する**。M6 と同じ単位 |
| M1〜M4 相当 | 同じ 2 枚を 1 セットとした評価値。M1〜M3 は平均まわりの散らばりなので**注入量の半分**、M4 は `a/(2+a)` |

### 摂動の正確さ（`tests/nail3dPerturbation.test.ts` / 31 ケース）

- 位置ずれ 2 / 5 / 10 / 20% が爪床長比で**厳密にその値**
- 傾き・回転 1 / 2 / 5 / 10 / 20° が**厳密にその角度**（法線の傾きは指軸を動かさず、指軸の回転は法線を動かさない）
- 寸法は指定した側だけが変わり、原点は動かない
- 摂動 0 で不変。退化 socket は NaN を返さずそのまま返す
- **軸が直交していない socket は直交化してから回す。** そうしないと「5°」のスライダーが実際には 5° 未満しか傾けず、**スライダーが誤差の大きさについて嘘をつく**

### この段階で得られないもの

| | |
|---|---|
| しきい値そのもの | オーナーの実測が要る。UI は値を**得るための道具** |
| 実写での妥当性 | 合成 fixture の手・爪で測っている。実写の質感・陰影で知覚は変わりうる |
| 1 本だけずれた場合の知覚 | 現状は 5 本すべてに同じ摂動をかける |

## 6-C. 入力契約と gap analysis — 2026-10-06

> 詳細: [SCAN_OBSERVATION_CONTRACT.md](./SCAN_OBSERVATION_CONTRACT.md)（仕様のみ・実装なし）

本計画 §1.3 の [1]（BenchTool からの JSON ダンプ）を仕様化し、既存パイプラインとの差分を洗った。
**本計画の前提が 2 点変わる。**

### 変更 1: 現状の出力では socket を推定できない（ただしマスクは存在する）

> **2026-10-06 訂正。** 初版はここで「ピクセルレベルの爪マスクは存在しない」と書いたが**誤り**だった。
> #389 のコメントで確認したところ、**`NailAngleMeasurer.swift` にピクセルレベルの爪マスクが実装済み**
> （`VNGenerateForegroundInstanceMaskRequest` の被写体マスク ＋ 肌色 chroma 判定）。
> #386 で「未着手」とされていた前景マスクは**検出経路の話**で、**角度スキャン経路とは別物**だった。

経路が 2 つある。

| | 検出経路（`NailDetector`） | 角度スキャン経路（`NailAngleMeasurer`） |
|---|---|---|
| ランドマーク | **あり**（21 点） | 言及なし（unknown） |
| 爪マスク | **なし**（0.32 補間の中心点とクロップ箱のみ / #356） | **あり**（ピクセルレベル） |

**socket 推定は両方を同じフレームで要する**（正準フレームにランドマーク、爪床にマスク）が、
**同一フレームで両方を出した実績は確認できなかった**。

そして爪マスクが覆うのは**見えている爪全体**で、**爪床と自由端を分ける処理は無い**。

**そのまま PoC を回すと意味のない「合格」が出る。** 骨格から作った点は爪が変わっても動かないため
**M6 は自動的に通り**、測っているのは socket の安定性ではなく**ランドマークの安定性**になる。
#356 が指摘するとおり 0.32 は固定係数で爪床の真の位置から系統的にずれるため、
**安定しているが間違っている**状態を「合格」と読んでしまう。

→ 対策: 契約で `source: "skeletonInterpolation"` を別物として記録させ、
socket 推定器は `regionType: "centerOnly"` と「自由端を分離できない `fullNail`」を**拒否**する。

### 変更 2: 2D→3D lift は独立した層として必要

`VNDetectHumanHandPoseRequest` は**2D 座標と confidence のみ**で深度を返さない。
Stage 1 の推定器は 3D 入力を前提にしていた（合成ハンドが 3D を与えていた）ため、
**実写では lift が必ず間に入る**。推定を A（観測・2D）/ B（lift・3D）/ C（正規化 socket）に
分離し、Layer A だけを保存して lift を差し替え可能にする。

### ブロッカー判定

| | 項目 | 対応 |
|---|---|---|
| **ブロッカー** | 爪床 / 自由端の分離 | ① 既存の爪マスクから導出（未検証）② 手動アノテーション（1 指 × 18 枚 = 72 点） |
| **要確認** | ランドマークと爪マスクを同一フレームで出せるか | 出せなければ写真間の位置合わせが新たな誤差源になる |
| 非ブロッカー | handedness / confidence / intrinsics | 代替・既定値・`missing` 明記で進む |

**PoC は BenchTool の大改修を待たずに開始できる。** しかも初版より見通しは良い ——
素材（ピクセル爪マスク）は既にあり **macOS ホストのベンチツールから呼べる**ので、
爪床の切り出しは「ゼロから作る」ではなく「既存マスクに境界判定を足す」話になる。


### 実測結果

#### 1. 再現性（本 PoC の第一目的）— **実質厳密**

カメラのスケール・画角・主点を変え、面内回転・平行移動・スケールを変えた 4 キャプチャ:

| M0 | M1 | M2 | M3 | M4 |
|---|---|---|---|---|
| 6.6e-15 | 7.1e-14 | 1.5e-6° | 1.7e-6° | 1.3e-15 |

**撮影条件が独立でも同じ socket が再現される。** これは Stage 1 の不変性が実際に lift を通して効いていることの確認でもある。

#### 2. lift bias（再現性とは別の問い）— **系統的で大きい**

| 手の傾き | landmarkRms | 爪床法線の誤差 | tiltRatio |
|---:|---:|---:|---:|
| 0° | 0.28 | **17.2°** | 0.00 |
| 10° | 0.46 | 27.2° | 0.00 |
| 20° | 0.69 | 37.2° | 0.00 |
| 35° | 1.01 | 52.2° | 0.00 |
| 50° | 1.29 | 67.2° | 0.00 |

**法線誤差が傾きと 1:1 で増える＝再構成された法線はまったく動いていない。** 原因は次の盲点。

#### 3. ⚠ 決定的な盲点: **爪床の幅軸まわりの傾きは単一視点で観測できない**

| 回転軸 | 射影の歪み（across·along） | 復元 |
|---|---|---|
| **指の長軸まわり** | 0 でない（10°で +452、50°で +1300） | **観測できる。** tiltRatio 0.73〜0.99（宣言どおり過小評価） |
| **爪床の幅軸まわり** | **全角度で厳密に 0** | **観測できない。** p = q = 0 のまま |

幅軸まわりの回転は、爪床を**歪ませずに短くするだけ**なので、
射影された四角形は正方のまま変わらない。**「短い正対した爪床」と区別がつかない。**

これは爪の pitch（反り・持ち上がり）方向そのものであり、**最も効いてほしい方向が最も見えない**。
foreshortening は `bedLength` に吸収され、法線はカメラ軸に留まる。

→ 対処として `residuals.bedSkewCosine` を追加した。**0 のときは「正対と測った」のではなく「測れなかった」**ことを意味する。
データ側でこれが見えるので、下流が誤って信用することはない。

#### 4. 奥行き事前分布の不一致が検出できている

無傾斜の姿勢で `clampedBones = 2`。汎用の指骨比がこの手に合っておらず、
射影長が事前分布より長い骨が 2 本ある。`depthResolved: false` として報告される。
**一般的な事前分布が個人に合わないことが、残差として可視化されている。**

### 評価軸の分離が実際に効いている

**lift は完璧に再現可能でありながら、系統的に間違っている。**
再現性（M0〜M4 ≈ 0）と lift bias（法線 17〜67°）が同時に成り立つのは、両方を別々に測っているから見える。
再現性だけを見ていたら「うまくいっている」と誤読していた。

### Layer B 差し替え可能性

`socketObservationsFrom()` は Layer B の出力を Stage 1 の `estimateSocket()` にそのまま渡す。
**Layer C（NormalizedNailSocket）と M0〜M6 は一行も変えていない。** `liftVersion` を上げて B を差し替えても下流は無改修。

### 正規化値と meter の分離（継続）

lift は画素単位で動き、Layer C で近位指骨長により正規化される。
**meter への変換経路は引き続き存在しない。** 画像サイズを 20 倍にしても `bedWidth` / `bedLength` が変わらないことをテストで確認済み。

## 6-E. Stage 4（2-view lift の最小 PoC）— 2026-10-07

Stage 3 で判明した「単一視点では原理的に観測できない自由度」——
爪床の**幅軸まわりの傾き（pitch）**——が、視点を 1 つ足すだけで observable になるかだけを確認した。
3D reconstruction 全体の構築ではない。SfM / photogrammetry / 動画処理 / 3 視点以上は対象外。

### 方針の確定: single-view は baseline として残し、最終方式候補から外す

`liftVersion: 1`（`weakPerspective+planarPalm+minimumTilt`）は**回帰比較用の baseline として保持**する。
盲点が構造的で、推定器の改良では解消しないため、**最終方式の候補ではない。**

### 解法

参照視点で `(Dx, Dy)`、第 2 視点で `b` として見える手首からのオフセット `D` について、
相対回転 `R`（既知）と未知のスケール比 `u` を使って:

```
bx = u*(r00*Dx + r01*Dy) + r02*(u*Dz)
by = u*(r10*Dx + r11*Dy) + r12*(u*Dz)
```

点ごとの深度を消去すると `u` のみの式が 1 点につき 1 本得られる（全対応点で最小二乗）。
`u` が決まれば深度は点ごとに解ける。**消去の分母は `(r02, r12)` に比例する**ため、
2 視点が近づくとゼロになる。degeneracy が推測ではなく代数に現れる。

### 実測結果

#### 1. pitch bias はどこまで減るか — **完全に消える**

第 2 視点を Y 軸まわり 25° に置き、合成 3D の爪床を ground truth として法線誤差を直接測定:

| hand pitch | v1 法線誤差 | v2 法線誤差 |
|---|---|---|
| 0° | 17.19° | **0.000°** |
| 10° | 27.19° | **0.000°** |
| 20° | 37.19° | **0.000°** |
| 35° | 52.19° | **0.000°** |
| 50° | 67.19° | **0.000°** |

**単眼の不可観測自由度は本当に回復する。** v1 の誤差は pitch に 1:1 で増えるのに対し、
v2 は無ノイズなら全 pitch で厳密。スケール比 `u` も仮定せず解いており、2 台のカメラ倍率比に一致する。

#### 2. view separation は何度から有効か — **合法になる角度と使える角度は大きく違う**

degeneracy 指標は `|(r02, r12)|`、すなわち第 2 視点が見える world Z 軸成分の長さ（= 面外分離角の sin）。
しきい値 `DEFAULT_MIN_VIEW_SEPARATION = 0.05`（約 2.9°）未満は `viewsTooSimilar` として**拒否**する。

ただし無ノイズでは 3° でも厳密に解ける。**実用上の分離角はノイズを入れないと見えない。**
視点ごとに独立な 5px のアノテーションノイズを与えた場合（8 試行平均）:

| 分離角 | sepIndex | v2 法線誤差 |
|---|---|---|
| 3° | 0.052 | 45.6° |
| 5° | 0.087 | 43.9° |
| 10° | 0.174 | 31.7° |
| 15° | 0.259 | 21.3° |
| 25° | 0.423 | 12.6° |
| 40° | 0.643 | 8.2° |
| 60° | 0.866 | 6.0° |

**3〜5° では v1 の盲点と大差ない。** 深度は第 2 視点の像で sepIndex 倍に縮んで現れるため、
アノテーション誤差が sepIndex で割られる。そこで observability を bool ではなく等級で返す:

| `separationQuality` | 条件 | 意味 |
|---|---|---|
| `degenerate` | < 0.05（約 2.9°） | 深度が決まらない。lift は `canonical: null` を返す |
| `weak` | 0.05 〜 0.42 | 解けるがアノテーション誤差を増幅する。数値を信用してはいけない |
| `adequate` | ≥ 0.42（約 25°） | 使える |

**運用指針: 2 視点の分離角は 25° 以上、できれば 40〜60°。**

#### 3. どちら方向の追加視点が情報量が高いか — **幅軸まわり（指の上下）**

同じ分離角 25°・同じ sepIndex 0.423 でも、方向で 1.7〜1.9 倍の差が出る（5px ノイズ・8 試行平均）:

| hand pitch | X 軸まわり（指の上下に動く） | Y 軸まわり（手を横切る） |
|---|---|---|
| 0° | **8.5°** | 15.5° |
| 20° | **7.2°** | 14.4° |
| 35° | **5.8°** | 12.6° |
| 50° | **4.4°** | 9.9° |

Z 軸まわり（roll）は sepIndex が**厳密に 0**。何度回しても像が回転するだけで world Z 軸は画像面に入らないので、
90° 回しても拒否される。

**撮影指針: 2 枚目は爪床の幅軸まわりに視点を動かす——指先の上方／下方から。手の横に回り込むのは効率が悪い。**

> ⚠ **Stage 5 でこの指針は覆った（§6-G F）。** 上記は「手が完全に静止している」前提での測定で、
> 指の屈曲軸が幅軸と一致するため、**指先上方のベースラインでは指の屈曲が完全に不可視のまま socket を壊す。**
> アノテーションノイズだけを見れば指先上方が有利だが、検出不能な誤差のほうが有害。現行の推奨は §6-G F。

#### 4. 入力誤差への感度

**アノテーションノイズ（視点ごとに独立）**: 分離角 25° で **1px につき約 2.5°** の法線誤差。

| 視点ごとの σ | v1 法線誤差 | v2 法線誤差 | v2 reproj |
|---|---|---|---|
| 0 px | 52.2° | 0.00° | 0.00 px |
| 1 px | 55.3° | 2.34° | 1.16 px |
| 2 px | 56.7° | 4.77° | 2.32 px |
| 5 px | 60.1° | 12.6° | 5.80 px |
| 10 px | 63.0° | 26.5° | 11.6 px |
| 20 px | 63.0° | 45.1° | 23.2 px |

⚠ **測定上の罠（1 度踏んだ）**: 3D の手を 1 回だけ摂動して 2 回射影すると、両視点の誤差が同一になり、
2-view lift はその「ノイズ入りの手」を厳密に復元する。全ノイズ水準で誤差 0.000 という
**ノイズ耐性があるように見えて実は共通オフセットを測っているだけ**の結果になる。
`jitterObservation()` を Layer A の 2D 観測に対して視点ごとに独立に適用して修正した。

**相対姿勢誤差**: ほぼ 1:1 で法線誤差に乗る。

| 相対姿勢誤差 | v2 法線誤差 | v2 reproj |
|---|---|---|
| 0.5° | 0.60° | ~1e-13 px |
| 1° | 1.19° | ~1e-13 px |
| 2° | 2.35° | ~1e-13 px |
| 5° | 5.68° | ~1e-13 px |
| 10° | 10.70° | ~1e-13 px |

#### 5. ⚠ 最重要の制約: **誤った相対姿勢は残差に現れない**

> **Stage 4.5 による限定（§6-F A）**: これは回転誤差の**全成分ではなく、ベースライン軸まわりの成分**について成り立つ。
> 他の 2 軸まわりの誤差は残差に現れる。ただし**残差に出ない成分こそが socket を最も壊す**ため、結論は変わらない。

姿勢誤差 10° でも **reprojection 残差は 1e-13 px**、スケール比 `u` も変わらない。
この方向については 2 視点正射影系が冗長性を持たないため、**誤った姿勢を深度に吸収して完璧に再射影する。**

したがって:

- **reprojection 残差を相対姿勢の検証に使ってはいけない。** アノテーションの一貫性しか測っていない
- **相対姿勢は画像の外（ARKit / IMU / デバイス odometry）から 1° 程度の精度で与える必要がある**
- `assumptions` にこの性質を明記した（`~1:1` / 残差に出ない）

これは実写段階の設計を決める。手持ちで任意の 2 枚を撮って後から姿勢を推定する経路は、
**この PoC の結論では成立しない。**

## 6-F. Stage 4.5（relative pose source の成立条件）— 2026-10-07

Stage 4 で「誤った relative pose が reprojection residual に出ない」ことが判明したため、
**relative pose を外部から何度の精度で与える必要があるか**を定量化した。
ARKit / IMU は**解決策として固定していない。** 測ったのは「何が必要か」であり、「何で供給するか」はその後の判断。

測定条件: 手を 35° pitch、参照視点は正対、第 2 視点は指先の上方 25°、カメラ距離は手の寸法の 2 倍、
weak perspective、index finger。誤差は**合成 3D から直接求めた socket**（ground truth）との差。

### Stage 4 の主張の限定: 不可視なのは「ベースライン軸まわりの成分」

ベースラインを X 軸（指先の上下）に取り、誤差軸を X から Y へ傾けながら 1° の姿勢誤差を注入:

| 誤差軸 | reproj 残差 | socket origin 誤差 |
|---|---|---|
| X から 0°（= ベースライン軸） | **0.000 px** | **3.42%** |
| X から 30° | 8.18 px | 3.03% |
| X から 60° | 14.37 px | 1.83% |
| X から 90° | 16.87 px | 0.15% |

**残差と被害がちょうど逆向き。** 3 自由度のうち 2 つは残差で検出できるが、
**最も socket を壊す成分（ベースライン軸まわり＝視点間角度そのものの誤差）だけが完全に不可視。**
Stage 4 で「全成分で不可視」と書いたのは測定条件（ベースラインと誤差軸が一致）に由来する過度な一般化だったので限定した。結論は変わらない。

### A. socket への誤差伝播（3 入力を独立に注入）

#### A-1. relative rotation error（ベースライン軸まわり・25° 分離）

| 姿勢誤差 | origin（爪床長比） | normal | tangent | bedWidth | bedLength | reproj |
|---|---|---|---|---|---|---|
| 0.25° | 0.86% | 0.05° | 0.05° | 0.61% | −0.18% | 0.000 px |
| 0.5° | 1.72% | 0.11° | 0.11° | 1.21% | −0.36% | 0.000 px |
| 1° | **3.42%** | 0.21° | 0.21° | **2.39%** | −0.72% | 0.000 px |
| 2° | 6.76% | 0.40° | 0.40° | 4.67% | −1.44% | 0.000 px |
| 5° | 16.24% | 0.88° | 0.88° | 10.78% | −3.53% | 0.000 px |

**⚠ 法線を見ていると要求精度を 10 倍以上過小評価する。**
Stage 4 では world 座標の爪床法線を測って 1:1 の伝播を見たが、canonical frame では
ランドマークも同じ誤った姿勢で歪むため**法線誤差の大半が同相成分として打ち消される**（1° あたり 0.21°）。
誤差は消えるのではなく **origin（3.42%/deg）と bedWidth（2.39%/deg）へ移動する。**
→ **pose 精度を決めるのは `T_pos` と `T_size` であって `T_normal` ではない。**

#### A-2. camera position error — 効くのは「視線方向」だけ

| 誤差 | 含意する角度 | origin | reproj |
|---|---|---|---|
| 視線に垂直 0.25% of d | 0.16° | 0.36% | 1.85 px |
| 視線に垂直 1% of d | 0.63° | 1.78% | 7.31 px |
| 視線に垂直 5% of d | 3.16° | 17.90% | 31.9 px |
| **視線方向に 1〜20% of d** | — | **0.00%** | **0.000 px** |

**手までの距離は知らなくてよい。** weak perspective ＋ スケール比を解いている以上、
視線方向への並進は視線方向を変えないので何も変わらない（20% ずらしても誤差 0）。

並進が効くのは視線方向を変える成分だけで、変換は単なる幾何: **δθ ≈ δ⊥ / d**。
距離 30 cm なら 1 cm の位置誤差が約 1.9°。**位置の要求は角度の要求よりはるかに緩い。**
なお横方向の位置誤差はベースライン軸と交差する向きに視線を倒すため、**残差に現れる**（検出可能）。

#### A-3. nail-bed annotation error（視点ごとに独立・12 試行平均）

| σ | origin | normal | tangent | bedWidth | bedLength |
|---|---|---|---|---|---|
| 0.5 px | 2.12% | 0.68° | 0.73° | 0.66% | 1.47% |
| 1 px | **4.22%** | 1.35° | 1.45° | 1.34% | 2.94% |
| 2 px | 8.38% | 2.70° | 2.90° | 2.73% | 5.86% |
| 5 px | 20.6% | 6.89° | 7.35° | 7.20% | 14.5% |

**1° の姿勢誤差 ≈ 0.8 px のアノテーション誤差**（3.42 vs 4.22 %/unit）。
**2 つの予算はほぼ同じ大きさで、pose 精度だけをアノテーション精度より先に詰めても意味がない。**

（参考: 同条件の single-view v1 は origin 136.7% / normal 27.3° / bedLength −36.9%。桁が違う。）

### C. 必要な pose 精度

`T_pos` / `T_size` は **§6-B の知覚較正で未実測（オーナー作業）** なので、逆算表の形で出す。
relative pose 誤差とアノテーション誤差を独立 2 源として二乗和で配分（各 `0.707 × T_pos`）:

| `T_pos` | 25° 分離 | 40° 分離 | 60° 分離 | 併せて必要なアノテーション σ（60°） |
|---|---|---|---|---|
| 3% | 0.62° | 0.93° | 1.25° | 0.83 px |
| **5%** | 1.03° | 1.56° | **2.08°** | **1.39 px** |
| **10%** | 2.07° | 3.11° | **4.16°** | **2.77 px** |
| 15% | 3.10° | 4.67° | 6.24° | 4.16 px |

**暫定の作業値（`T_pos` 実測までの仮置き）**: 分離角 40〜60° で **relative pose 精度 2〜4°**、
アノテーション σ 1.5〜3 px。距離 30 cm 換算で**カメラ位置は手に対して約 1 cm**。

この予算は **device odometry の誤差と手の動きの両方**を含む（下記 D-0）。

### D. capture model の区別 — ARKit が観測するのは camera motion、必要なのは camera-to-hand

#### D-0. 前提となる実測: **手が動くことは pose が間違っていることと同じ**

姿勢は正しく与え、代わりに 2 枚の間で手を回した場合:

| 手の回転 | 軸 | origin 誤差 | reproj | 同角度の pose 誤差での origin |
|---|---|---|---|---|
| 0.5° | X（ベースライン軸） | 1.71% | **0.000 px** | 1.72% |
| 1° | X | 3.38% | **0.000 px** | 3.42% |
| 2° | X | 6.60% | **0.000 px** | 6.76% |
| 1° | Y | 2.13% | 11.8 px | — |

**数値まで一致する。** つまり relative pose 予算は
`device odometry 誤差 ⊕ 手の動き` の合計で、しかもベースライン軸まわりの手の動きは**残差に出ない。**

#### D-1. 三つのモデル

| | A. 手が静止 / カメラが動く | B. カメラが静止 / 手が回る | C. 両方動く |
|---|---|---|---|
| **直接観測できるもの** | camera-to-world の相対姿勢（VIO / IMU）。手が world に固定されているので **camera-to-hand の相対回転と一致する** | **何もない。** odometry は「カメラは動いていない」＝相対姿勢ゼロと報告するが、実際の camera-to-hand は手の回転ぶん変化している | camera motion のみ。必要なのは `camera motion ⊖ hand motion` で、**後者が未観測** |
| **画像から推定が必要なもの** | pose については不要。ただし**手が本当に静止していたかの検証**が必要 | **relative pose の全部**（＝手の回転）。21 landmarks から推定するしかない | 同上。**C は推定すべき量としては B に帰着する** |
| **Stage 4 の lift へ渡せるもの** | ARKit の相対回転をそのまま | 渡せるものがない。landmark 由来の推定値のみ | odometry 値は**誤差の上界すら与えない**。landmark 由来の推定値のみ |
| **誤差を自己検証できるか** | **部分的。** 3 自由度のうち 2 つは reproj 残差で検出できるが、ベースライン軸まわりは不可視 | 同上（残差の性質は pose の出所に依らない） | 同上 |

**ARKit を単独の pose source にできるのはモデル A だけ**で、しかも「手が静止している」が
**上表 D-0 の予算（2〜4°）の中で**成り立っている必要がある。
支えのない手は 1 秒で数度ドリフトしうるので、**A は撮影姿勢で作り込まない限り成立しない。**

### E. 21 landmarks から view 間の相対姿勢を推定する場合（未実装・自由度の整理のみ）

2 視点 weak perspective、点数 N、手は 2 枚の間で**剛体**と仮定:

| | |
|---|---|
| 未知数 | 相対回転 3 ＋ スケール比 1 ＋ 点ごとの深度 N = **N+4** |
| 方程式 | 第 2 視点の x, y = **2N**（第 1 視点は構造の x, y の定義に使われる） |
| 21 landmarks | 42 本 vs 25 未知数 → **優決定** |

**観測可能**:

- 相対回転 3 自由度（一般の配置で）——ただし **depth reversal（Necker）の 2 値縮退**が残る。
  `handedness` と「背側がカメラを向く」事前知識で解消できる（Nailous は両方持っている）
- **手の動きとカメラの動きの区別は不要。** 画像にとって両者は同一であり、推定されるのは
  まさに必要な **camera-to-hand** の相対姿勢。**→ モデル A / B / C を区別せず同じ経路で扱える**

**観測不可能 / 条件付き**:

| | |
|---|---|
| 絶対スケール・絶対深度 | 回復しない（Stage 4 と同じ。metric 変換は引き続き対象外） |
| 剛体性の破れ | 2 枚の間で**指が曲がる**と、その変形は回転誤差として吸収され、**区別する手段がない** |
| 条件数 | 手の奥行き方向の広がり（背腹 2〜3 cm）は幅・長さ（15 cm 級）より一桁小さい。**浅い構造 × 小さい分離角**は古典的な bas-relief 的悪条件で、弱く決まるのはまたしても**ベースライン軸まわりの成分**。**未測定 — Stage 5 の主問題** |
| 循環参照 | landmarks から姿勢を推定すると、その landmarks の reproj 残差は定義上ほぼ 0 になり検証に使えない。**ただし爪床 4 点は姿勢推定に使っていないので、爪床の残差は独立した検証量になる** |

### F. Stage 4.5 の結論 — どの撮影 UX なら必要精度を供給できそうか

要求をまとめると:

1. 分離角 **40〜60°**（狭いほど両方の感度が上がる。これが最優先）
2. 第 2 視点は**爪床の幅軸まわり＝指先の上方／下方**（Stage 4 §6-E 3）
3. camera-to-hand の相対回転を **2〜4°**（`T_pos` 実測で確定）。**手の動きもこの予算に含む**
4. 手までの距離は**不要**。カメラ位置は手に対して約 1 cm（30 cm 換算）
5. 2 枚の間で**指の関節が動かない**こと（landmark 経路を使う場合の必須条件）

| 撮影 UX 候補 | 分離角 | 手の静止 | pose source | 評価 |
|---|---|---|---|---|
| **手を台に置き、端末を正面→指先上方 45° へ動かす** | 作りやすい | **台で機械的に拘束** → 予算内に収まる見込み | odometry と landmark の**両方**が使える | **第一候補** |
| 手を宙に保持し端末を動かす | 作りやすい | 支えがなく数度ドリフト。名目 A・実質 C | odometry は誤差の上界すら与えない | 却下寄り |
| 端末を固定し手を回す（モデル B） | ユーザー次第 | 宙に保持することになり同上 | landmark のみ | 次点 |
| 物理的な治具／マットの指定位置から 2 枚 | 設計で固定 | 台に置くので良好 | **構成から既知** | 精度は最良。UX コストが高い |

**第一候補: 「手を平らな面に置き、端末を正面から指先の上方 45° 付近へ動かして 2 枚撮る」。**

> ⚠ **Stage 5 で視点方向のみ変更（§6-G F）。** 「手を置く」は Stage 5 でさらに重要になったが、
> **移動方向は「指先の上方」ではなく「手を横切る方向寄りの斜め」に変更。** 理由は §6-G F。
> また landmark 由来の姿勢は**回転軸しか与えない**ことが判明したため、
> 「独立した 2 つの推定値」という前提も軸成分に限定される（§6-G E）。

手を置くという一点が、(a) モデル A を名目でなく実際に成立させ、(b) landmark 経路が要求する剛体性も同時に満たす。
さらにこの構成では **odometry 由来の姿勢と landmark 由来の姿勢という独立した 2 つの推定値が揃う**。

> ⚠ **Stage 6 でこの前提が変わった（§6-H E-6）。** 既知 Personal HandProfile があれば相対回転は画像から
> median 0.2° で測れるため、**odometry はクリティカルパスから外れ、交差検証に降格できる。**
>
> **不可視成分に対する唯一の検証手段は、この 2 つの独立な推定値の突き合わせ。**
> 画像単独の残差はベースライン軸まわりを原理的に police できない（§6-F A）。
> したがって **ARKit は「pose source」としてではなく「landmark 由来推定の交差検証」として価値がある** ——
> この順序づけが Stage 4.5 の実質的な結論。

## 6-G. Stage 5（landmark からの relative rotation 推定）— 2026-10-07

Stage 4.5 の「21 点なら 42 方程式 > 25 未知数だから観測可能」という**仮説を実測で検証した。結論は偽。**
しかも conditioning の問題ではなく、**厳密な 1 パラメータ縮退**だった。

|---|---|---|
| **A. all21** | 全ランドマーク | 21 |
| **B. palmRigid** | `wrist` / `thumbMCP` / `indexMCP` / `middleMCP` / `ringMCP` / `pinkyMCP` | 6 |

母指側に幅を与える唯一の palm 点なので入れた。

実装: `src/lib/nail3dLandmarkPose.ts` / テスト: `tests/nail3dLandmarkPose.test.ts`（22 ケース）。
**爪床 semantic landmarks は入力型（`PoseLandmarkView`）に存在しない** ——

### A. 仮説が偽である理由と、その実測

**方程式の数え方が間違っていた。** 深度は第 2 視点の像に `(r02, r12)` という**1 方向からしか入らない**。
その方向では各点の深度が各点の式を 1 本ずつ食い潰し、**冗長性がゼロ**。
回転についての情報は直交成分にしかなく、そこが決めるのは**回転軸の向きだけで、大きさではない**。
大きさは深度スケールと厳密にトレードオフする（古典的な bas-relief 縮退）。
**点を増やしても、もともと冗長性があった方向の冗長性が増えるだけ。**

最適化器を一切介さない直接確認（合成手の非平面性は rms 0.0688 hand unit / xy 範囲 1.0 なので、平面ではない）:

| 仮定した分離角 | 残差 rms |
|---|---|
| 5° | 2.95e-13 px |
| 15° | 2.58e-13 px |
| 25°（真値） | 2.68e-13 px |
| 40° | 2.66e-13 px |
| 70° | 2.86e-13 px |

**完全に平坦。** 一般軸（X から 30° 傾けた軸）でも同じで、**真値から 50° 離れた位置に厳密解が存在する**。
いっぽう**軸を間違えると残差は出る**（真 25°/X に対し Y 軸 42 px、X+Y 45° 軸 82 px、roll は ∞）。
→ 軸は観測可能、大きさは観測不能。

#### 幾何を変えても一切改善しない

| 手の形状 | 大きさの観測可能性 |
|---|---|
| palmArch 0（平らな手のひら）/ 0.08 / 0.15 / 0.25（深いアーチ） | すべて weakPx/deg = 0 |
| depthScale 0.5（薄い手）/ 2.0（厚い手） | 同じ |
| 指の長さ比を ±25% 変動 | 同じ |

**conditioning 問題なら手を厚くすれば直る。直らない。構造的縮退である証拠。**

#### 推定器は「きれいな残差」を根拠にしない

残差 ~1e-13 px でも真値から数十度ずれるため、推定器は
**`weakestPxPerDeg < OBSERVABLE_MIN_PX_PER_DEG`（0.1 px/deg）なら `rotation` を返さず `refusedReason: 'notObservable'` を返す。**
`discardedRotation` には当てはめ結果を診断用に残すが、その大きさは測定値ではない。

| 条件（全分離角 10/25/40/60°、両方式） | 結果 |
|---|---|
| `refusedReason` | `notObservable` |
| `rotation` | `null` |
| `confidence` | 0 |
| `conditionNumber` | ∞ |
| 誤差の直交成分 | **0.00°**（median/p95/worst すべて） |
| 誤差のベースライン軸成分 | 1.25〜83.8°（幾何を変えると数十度さまよう＝未拘束の証拠） |

### D. ⚠ Stage 4 の推奨ベースライン方向が裏返る

**ただし上記は「ベースラインが屈曲軸と一致しない場合」。一致する場合（＝ Stage 4 が推奨した指先上方）は話が逆転する。**

指の屈曲軸は爪床の幅軸、つまり Stage 4 が「最も情報量が高い」と測った第 2 視点の移動軸と**同じ**。
その結果、**屈曲は完全に不可観測な方向に落ちる**:

正しい姿勢を lift に与え、index を 1° 曲げただけの場合（分離角 40°）:

| 第 2 視点の方向 | socket origin 誤差 | socket normal 誤差 | lift 残差 | landmark 姿勢の残差 |
|---|---|---|---|---|
| **elevation 40°（指先上方 = Stage 4 推奨）** | **8.58%** | 1.54° | **0.000 px** | **0.000 px** |
| diagonal 20°/35° | 8.46% | 1.50° | 2.22 px | 1.95 px |
| diagonal 28°/28° | 7.58% | 1.37° | 3.31 px | 2.94 px |
| **diagonal 35°/20°** | **5.78%** | 1.11° | 4.26 px | 3.72 px |
| **azimuth 40°（手を横切る）** | **1.95%** | 0.50° | **5.19 px** | **4.34 px** |

**指先上方では、1° の屈曲が socket origin を 8.58% 動かしながら、残差はどこにも出ない。**
Stage 4.5 の暫定 `T_pos` 予算（5〜10%）を 1° の指の動きだけで食い潰し、しかも検出できない。
azimuth 方向なら被害は 1/4.4 で、かつ明確に検出できる。

**単調なトレードオフで、両取りできる点はない。** azimuth に寄せるほど屈曲被害は減り検出性は上がる
（Stage 4 のアノテーションノイズ耐性は逆に下がる）。
`diagonal 35/20`（azimuth 優勢の斜め）は **elevation より被害が小さく（5.78% < 8.58%）かつ検出可能**なので、
elevation に対して純粋な改善。

### E. 結論

#### 1. 21 点方式は成立するか → **relative rotation 全体としては不成立。軸のみ成立。**

大きさは**厳密に観測不能**で、点数・手の形・分離角のいずれでも解決しない。
いっぽう**軸の向きは分離角 40° / σ2px で median 0.85° / p95 2.93°** と Stage 4.5 予算内。
**3 自由度のうち 2 つは供給できる。**

#### 2. palm-only は成立するか → **不成立。**

同じ縮退を持つうえ、軸の精度も **p95 20.8°** で予算外、さらに手の形で 4 倍変動する。
**finger articulation への完全な耐性だけが長所。**

#### 3. どちらを primary estimator にすべきか → **primary は置けない。all21 を「軸の推定器＋非剛体検出器」として使う。**

relative pose を landmark だけで供給する計画は破棄する。all21 の役割は 2 つ:

- **回転軸の推定**（予算内）
- **残差による非剛体検出**（屈曲 1° で 2.9〜4.3 px、アノテーション 2px の床 2.6px に対して検出可能）

palmRigid は **all21 の残差が屈曲を示したときの対照**として保持する価値がある
（屈曲に完全不感なので、A と B の軸が食い違えば屈曲が原因と切り分けられる）。primary ではない。

#### 4. external pose との disagreement を scan rejection に使えるか → **軸成分のみ使える。**

`poseDisagreement()` は誤差を軸成分と直交成分に分けるが、
**意味があるのは `orthogonalDeg` だけ**（軸方向の大きさについて landmark は何も言っていないので、
`baselineAxisDeg` は external 値を何とも比較していない）。
そのため `axisDisagreementDeg()` を別に用意した —— これが画像に裏付けられた唯一の交差検証量。

実用的な棄却レシピ:

| 信号 | 検出できるもの | 感度 |
|---|---|---|
| all21 の残差 | 手の非剛体変形（指の屈曲） | 屈曲 1° ≈ 2.9〜4.3 px（σ2px の床は 2.6 px） |
| `axisDisagreementDeg(landmark, external)` | 回転軸の不一致（手の剛体回転、odometry 誤差の直交成分） | 自身のノイズが p95 2.93° なので閾値 3〜4° |
| 爪床の lift 残差 | 爪床付近の局所的な破れ（姿勢推定に爪床を使っていないので独立） | azimuth 方向なら屈曲 1° で 5.19 px |
| **回転の大きさ** | **何も検出できない** | — |

**つまり scan rejection は「軸のずれ」と「非剛体変形」は捕まえられるが、「分離角そのものの誤り」は原理的に捕まえられない。**
そこは構成で保証するしかない。

#### 5. Stage 5 の結果から推奨 capture UX を変更する必要があるか → **ある。視点の移動方向を変える。**

| | Stage 4.5 の推奨 | Stage 5 後の推奨 |
|---|---|---|
| 手の支え | 平らな面に置く | **変更なし（むしろ必須性が上がった）** |
| 視点の移動方向 | 正面 → 指先の上方 45° | **正面 → 手を横切る方向寄りの斜め（azimuth 35° / elevation 20° 程度）** |
| 分離角 | 40〜60° | **変更なし** |
| pose source | odometry と landmark の 2 つを交差検証 | **大きさは odometry（または構成）のみ。landmark は軸の検証と非剛体検出に限定** |

変更理由は 2 つだけ:

1. **指先上方は、指の屈曲を不可視にしたまま socket を壊す**（§D）。斜め〜横方向なら被害が 1/4 で検出可能。
2. **landmark は回転の大きさを供給できない**（§A）ので、「2 つの独立な推定値」は軸成分に限られる（§E-4）。

「手を平らな面に置く」はさらに重要になった。これが同時に効く対象が 3 つある:
手の剛体的な静止（Stage 4.5 D-0）、**指の屈曲の抑制**（Stage 5 C/D）、そして
**検証不能な回転の大きさを撮影構成の側で決めてしまえる可能性**（治具・マットなら構成から既知。§6-F F の第 4 候補）。

| 射影モデル | **両視点とも weak perspective。縮退はこのモデルに固有で、真の透視投影では破れる。** 透視での可観測性は未測定 —— landmark 経路を復活させうる唯一の筋 |
| 既知 HandProfile | 個人の 3D ランドマークが既知なら点ごとの深度が未知でなくなり縮退しない。**未測定。** Nailous は HandProfile を Canonical に持っているので筋はある |

## 6-H. Stage 6（Canonical Personal HandProfile を既知 3D prior として使う）— 2026-10-07

Stage 5 の縮退の原因は「点ごとの深度が未知」であることだった。それを取り除く手段を Nailous は既に持っている ——
**HandProfile は Canonical data**。既知 3D 形状があれば各視点は structure-from-motion ではなく**姿勢あてはめ**になる。
回転 3 ＋ スケール 1 ＋ 並進 2 に対して測定値 2N、**点ごとの未知数はゼロ**。

実装: `src/lib/nail3dProfilePose.ts`（`twoViewOrthographic+knownHandProfile`）/ テスト: `tests/nail3dProfilePose.test.ts`（26 ケース）。
視点ごとの姿勢は**閉形式**で解く（線形最小二乗 → SVD による Procrustes 射影 → 第 3 行は外積の符号＝深度分岐）。
SO(3) を探索しないのは速度のためではない: **粗い探索は「深いが誤った谷」を綺麗な残差付きで報告し、
それは Stage 6 が検出しようとしている縮退と区別がつかない。**

比較した 3 条件: **A. 本人の正確な profile / B. 1 パラメータずつ狂った profile / C. generic profile（別人の手）。**

### A. 縮退は本当に消えるか → **消える**

### B. HandProfile はどれだけ狂ってよいか

diagonal 40° / 2px / 16 試行、baseline-axis 誤差の median と profile mismatch:

|---|---|---|

| palm width +2% | 0.75° | 3.67 |
| **palm width +5%** | **1.83°** | 4.58 |
| **palm width +10%** | **3.70°** | 7.54 |
| palm width +20% | 7.65° | 13.88 |
| 横アーチ 0.15→0.13 | 0.11° | 4.96 |
| 横アーチ 0.15→0.08 | 0.21° | 12.86 |
| **横アーチ 0.15→0（完全に平ら）** | **0.47°** | 26.96 |
| 横アーチ 0.15→0.25 | 0.16° | 17.55 |
| 厚み ×1.1 / ×1.25 / ×1.5 | 0.22 / 0.53 / **1.07°** | 6.19 / 13.13 / 24.82 |
| 厚み ×0.7 | 0.44° | 16.02 |
| 指長 ±2 / ±5 / ±10% | 0.32 / 0.67 / **1.02°** | 8.74 / 20.26 / 39.87 |
| 指長 ±20% | 0.77°（total 3.13°） | 78.15 |
| MCP 位置ずれ 0.5 / 1 / 2% of 幅 | 0.14 / 0.15 / 0.34° | 4.56 / 6.72 / 11.98 |
| MCP 位置ずれ 5% | 0.86°（total 2.63°） | 29.07 |

#### B-1. **絶対スケールは不要（確認）**

global scale を ±20% 狂わせても**結果が 1e-6 度まで同一**。視点ごとにスケールを解いているので一様な拡大縮小は完全に吸収される。
**profile が供給するのは形（shape）であって大きさ（size）ではない。** mm 単位の情報は一切要らない。

#### B-2. 拘束するのは palm width —— 正確には**縦横比**

palm width 誤差だけが突出して効く。理由は明確で、**palm width の誤差は手の縦横比（aspect ratio）の誤差であり、
縦横比の誤差は foreshortening と区別がつかない。** foreshortening こそが回転として読まれるので、直接回転誤差に化ける。
いっぽう global scale は縦横比を変えないので無害 —— この 2 つが分離できたことが B の主結果。

**必要な Personal Hand Calibration 精度（逆算）:**

| パラメータ | 2° 予算 | 4° 予算 |
|---|---|---|
| **palm width / 手長の縦横比** | **±5%** | **±10%** |
| 厚み（背腹方向） | ±100% 超 | — |
| 横アーチの深さ | 任意（平らでも 0.47°） | — |
| 指の長さ比 | ±20% 超 | — |
| MCP 位置 | 幅の ±5% 超 | — |
| **絶対スケール** | **不要** | **不要** |

→ **較正で真面目に測る必要があるのは縦横比ひとつだけ。** 手のひら幅 8cm なら 5% は 4mm 相当。

#### B-3. ⚠ mismatch 残差は、最も重要なパラメータに対して最も鈍い

mismatch 残差は profile 誤差の自然な検出器だが、感度が逆向きについている:

| | baseline-axis 誤差 | mismatch（床 3.44px に対して） |
|---|---|---|
| 指長 ±5% | 0.67°（ほぼ無害） | 20.3 px（**5.9 倍・大騒ぎ**） |
| palm width +5% | **1.83°（予算の半分）** | 4.58 px（**1.3 倍・ほぼ無音**） |

**縦横比の誤差は、予算を食い潰す大きさでも残差にほとんど出ない。**
したがって mismatch 残差は profile 検証の十分条件にならず、**縦横比は較正時に測って確定させるしかない。**
（`maxProfileMismatchPx` による拒否は用意したが既定では無効。Stage 6 は閾値を仮定せず測定した）

generic = 横アーチ 0.09（本人 0.15）・palm width +12%・厚み ×0.8・指長 −12〜+20%

ただし **mismatch が 52px（正確な profile の 15 倍）なので「この profile は本人のものではない」ことは明確に検出できる。**
また有限で軸も正しく、landmark-only（何も返せない）より確実に良い。

→ **generic profile は初回フォールバックとしては成立するが、常用すると socket origin を 15〜21% 動かす。**

all21 のほうが依然 3〜4 倍良いが、palmRigid も予算内（p95 1.45°）に収まった。
（既知形状では**4 点でも解ける** —— 点ごとの未知数が無いため。テストで確認済み）

all21 が屈曲を検出し、palmRigid が屈曲に影響されない値を与える。片方を選ぶより両方走らせるほうが情報量が多い。

### E. 結論

#### 1. Personal HandProfile で ambiguity は本当に消えるか → **消える**

残差は真値を頂点とする V 字（1.2px → 両側 190〜270px、傾き 7.6px/deg）、conditionNumber は ∞ から **1.8〜2.5** へ、
confidence は 0 から **0.95** へ。**profile を外すと同じデータで厳密縮退が再発する**ことも固定済み。
精度は median 0.2° / p95 0.5° / worst 0.6° で、**予算 2〜4° に対し一桁以上の余裕。**

#### 2. 必要な HandProfile 精度 → **縦横比ひとつだけ。±5%（2°）/ ±10%（4°）**

絶対スケールは**不要**（±20% で結果が 1e-6 度まで同一）。
厚み・横アーチ・指長比・MCP 位置はいずれも 2〜20 倍のゆるさがあり、実用上の較正誤差では問題にならない。
**⚠ ただし縦横比の誤差は mismatch 残差にほとんど出ない**ので、較正時に測って確定させる必要がある（検出に頼れない）。

#### 3. generic profile でも実用になるか → **主経路としては不足、初回フォールバックとしては可**

baseline-axis 4.6〜5.5° で予算外。socket origin を 12.8〜18.6% 動かす。
ただし mismatch 52px で「本人のものでない」ことは明確に検出でき、landmark-only より確実に良い。
**「generic で開始し、mismatch が高いので較正を促す」という製品フローは成立する。**

#### 4. articulation に対して all21 / rigid subset のどちらがよいか → **all21 を primary、palmRigid を併走**

Stage 5 後推奨の diagonal 方向では、屈曲 5° でも all21 の baseline-axis は 0.35° に留まる（誤差が直交成分＝検出可能側に落ちる）。
palmRigid は屈曲に完全不感だが baseline-axis 0.67° で常時やや劣る。
**両方走らせると: all21 が精度と屈曲検出（mismatch 8 倍）を、palmRigid が屈曲非依存の対照を与える。**
なお socket 被害自体は set に依らないので、articulation は依然として**棄却**で扱う。

#### 5. Stage 5 後の capture UX を維持できるか → **維持できる。理由が 1 つ増えた**

| | Stage 5 後 | Stage 6 後 |
|---|---|---|
| 手を平らな面に置く | 必須 | **変更なし**（屈曲被害は姿勢が正確でも消えない。§D-3） |
| 視点の移動方向 | azimuth 優勢の斜め | **変更なし。理由が追加**: diagonal は屈曲誤差が検出可能な直交成分へ落ちる唯一の方向（§D-2） |
| 分離角 40〜60° | 推奨 | **姿勢供給としては 25° でも足りる。** 40〜60° の根拠は Stage 4.5 のアノテーション感度のみに戻る |
| pose source | 大きさは odometry または構成のみ | **images から供給できる。odometry は交差検証へ降格（§6-F F の順序づけが実現可能になった）** |

#### 6. 初回 Hand Calibration を製品要件にする価値があるか → **ある。最も効果の大きい 1 手**

較正を入れると relative pose が
「外部から 2〜4° で供給しなければならず、しかも検証できない量」から
**「画像から median 0.2° で測れて、残差が妥当性を示す量」**に変わる。帰結:

- **ARKit / IMU がクリティカルパスから外れる。** Stage 4.5 の「odometry は pose source ではなく交差検証」という順序づけが実際に成立する
- capture model A / B / C の区別が不要になる（画像が camera-to-hand を直接測るため。§6-F D-1 の懸念が解消）
- 較正で必要なのは**縦横比を ±5%** だけ。手のひら幅 8cm なら 4mm 相当で、専用機材は要らない
- 日常 scan の残る誤差源は**アノテーション精度と指の屈曲だけ**になる

**Stage 6 の実質的な結論: 初回 Hand Calibration は「あると便利な機能」ではなく、2-view 経路を成立させる前提条件。**

| HandProfile の取得方法 | **対象外（意図的）。** Stage 6 は「既知 profile が日常 scan をどれだけ簡単にするか」だけを測った |
